# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a **data repository**, not an application repository. It stores the raw survey data behind a "commonsense" research study as chunked CSV files, plus the scripts (in `.scripts/`) used to pull, join, analyze, and visualize that data. There is no build system, no test suite, and no linter — most of the repo is data or one-off analysis notebooks.

## Data layout (repo root)

Each top-level folder is one database table, dumped as CSV chunks named `<table>_<n>.csv` (chunks are capped at 90MB by `.scripts/pull_data.py`; a table may have multiple numbered files):

- `statements/` — active statements running on the platform.
- `statementproperties/` — six binary properties per statement for the design-point experiment (`fact`, `physical`, `literal_language`, `positive`, `knowledge`, `everyday`).
- `answers/` — participant answers to commonsense questions, keyed by `sessionId`.
- `experiments/` — which statements were assigned to which participant, keyed by `experimentId`.
- `individuals/` — CRT and RMET (Reading the Mind in the Eyes) responses, keyed by `sessionId`.
- `demo_matches/` — precomputed output of the session-matching process described below (notably `all_matches_hungarian.csv`).
- `sampling_by_country/` — precomputed rating-frequency stats used for recruitment sampling.

`statements/` and `statementproperties/` currently fit in one chunk each, and several consumers hardcode `_1.csv`: `server.py`, `statement_coverage.py`, `statement-generation/gap_analysis.py`, `statement-generation/judge_published.py`, the Dockerfile's `COPY` lines, and `besample/sampling_*/simulate_budget.py`. If `pull_data.py` ever rolls either table over to a `_2.csv`, all of those need updating.

To load a table in Python, concatenate its chunk files (see `.scripts/utils/load_data.py`; the root `README.md` has a snippet too, but its "100MB chunks" and "join on `sessionId`" claims are wrong). Its `load_individuals()`, `load_answers()`, `load_statements()`, `load_statements_properties()`, and `load_experiments()` helpers each assume they're called from a script one directory below repo root, e.g. from `.scripts/`.

**Critical data quirk — `sessionId` is not a reliable join key.** A bug during data collection caused the platform to mint a *new* `sessionId` for each survey step (ratings → CRT → RME → demographics) for a large fraction of participants, instead of reusing one `sessionId` per person. Only ~7.5k of ~45k participants have a consistent `sessionId` across all four record types; the rest must be re-linked using `startAt` (≈ `createdAt − secondsElapsed`, derived from the `experimentInfo` JSON blob) via a Hungarian-algorithm matching step. See `.scripts/matching_process.md` for the full explanation. **Always check whether a script needs `demo_matches/all_matches_hungarian.csv` to join `individuals`/`answers`/`experiments` correctly** — joining directly on `sessionId` silently drops most non-matching participants.

`all_matches_hungarian.csv` is produced by `.scripts/recover_demo_hungarian.py` (run from `.scripts/`; needs `scipy` and `tqdm`). It is run **manually, never by CI**, so participants affected by the bug who arrived after its last run don't appear in the explorer until it is rerun. Participants whose `sessionId` stayed consistent are picked up automatically. `update-data.py` asserts that the consistent-ID cohort is disjoint from every ID in the matches file. A stale or hand-edited matches file can therefore fail the CI "Build visualize data" step.

## Data pipeline (automated)

`.github/workflows/pull-data.yml` runs on push to `main`, on a cron (every other day, 00:00 UTC), and on manual dispatch. It:

1. Temporarily whitelists the runner's IP in an AWS security group, then runs `.scripts/pull_data.py` to pull new rows (by `id`) from the MariaDB/RDS database for each table in `TABLES` and append them to the chunked CSVs at repo root. `.scripts/metadata.json` tracks the last-pulled `id` per table — `pull_data.py` verifies this against the actual CSV contents before pulling and will `sys.exit(1)` if they disagree, so don't hand-edit the CSVs or `metadata.json` without keeping them in sync.
2. Commits the updated data (`git commit -m "Updated data at $(date)"`).
3. Rebuilds the `.scripts/visualize/` app's data files (`update-data.py`; baked into the image, not committed), builds its Docker image, pushes to ECR, and force-redeploys the ECS service (`common-sense-cluster` / `common-sense-service`). The ECS task definition itself lives in a different repo and is never edited here.

Runtime deps for the CI pull step are pinned in `.scripts/requirements.txt` — keep it minimal (only what `pull_data.py` needs). Notebook/analysis tooling (Jupyter, matplotlib, scipy for non-CI use, etc.) belongs in a local `.venv`, not this file — it previously pulled in unused, vulnerable packages when added here.

To run `pull_data.py` outside CI, run `python .scripts/pull_data.py` from the repo root, because it resolves `metadata.json` and the table folders relative to the working directory. It reads `DB_USER`, `DB_PASSWORD`, `DB_HOST`, and `DB_NAME` from the environment or a `.env` file (`DB_PORT` is set in CI but ignored), and the RDS security group only admits whitelisted IPs.

`pull_data.py` also strips emails out of the `urlParams` column for the `experiments` and `individuals` tables before writing — do not reintroduce raw `urlParams` data for those tables.

## `.scripts/visualize/` — Commonsense Survey Explorer

A self-contained, no-framework web app (Python stdlib `http.server` + vanilla JS + Chart.js) that serves interactive views over the survey data. This is the most actively developed part of the repo. Read `.scripts/visualize/README.md` first for setup and the API reference. `.scripts/visualize/handoff.md` has deeper implementation notes (CSS gotchas, cache-key history, per-panel architecture) but may lag recent changes (e.g. it predates the "Home" panel), so verify against the code before trusting specifics from it. The visualize `README.md` is also partly stale: its Deployment and CI/CD sections describe an EC2/systemd/GitHub Pages setup that the ECS pipeline above replaced.

Key facts:

- **No database at request time.** `server.py` loads `data/answers.csv`, `data/crt_rme_demo.csv`, `data/statement_properties.csv`, and `../../statements/statements_1.csv` into memory at startup; all `/api/*` endpoints compute scores on the fly and cache expensive results in-process (a plain `dict`), so a restart is needed to pick up new data or code changes to `server.py`/`utils.py`. Static file changes (`static/`, `index.html`) take effect on refresh alone. Data paths can be overridden with the env vars `DATA_DIR`, `STATEMENTS_PATH`, `REPO_ROOT` (read by `gap_analysis.py`), `STATEMENT_GEN_DIR`, and `STATEMENT_AUDIT_DIR` (read by `statement_audit.py`; defaults to `STATEMENT_GEN_DIR/existing/published`). The Docker image sets these because it places vendored files flat under `/app`, so any new file read from outside `visualize/` needs both a `COPY` line and an override that works in the container. Any path other than `/`, `/static/*`, or `/api/*` falls back to serving `index.html`, so panel routes such as `/statement_generation` are resolved client-side in `app.js`. A new panel needs no server route, only a `TAB_SLUGS` entry and a toggle line in `switchToTab()` (both in `app.js`) plus a `panel…` div in `index.html`. The top bar's `.tab-bar` lists only six panels: Home is the title button, the "Test yourself" button beside the tabs is an external link (see the layout bullet), and the three statement-generation pages are reached through in-page links (Design Points → Design Point Coverage → Published Statement Audit → TypeSafe Judgments). Those links in `index.html` are relative hrefs with no leading `/` (e.g. `href="statement_audit"`), so they resolve under `/report/` in production; keep new ones relative for the same reason as the API rule below.
- **Build the data files before running the server:** `cd .scripts/visualize && python update-data.py`, then `python server.py [port]` (default 8080). Use Python 3.12 (matches CI). On top of `.scripts/requirements.txt`, the server needs `PyYAML` (`server.py` imports `statement_coverage`, which imports `yaml`, at startup). `scipy` is optional: `server.py` uses it for exact t-critical values in the Design Points confidence intervals and falls back to a lookup table without it. `update-data.py` needs only pandas. `update-data.py` joins `individuals/`, `answers/`, and `demo_matches/all_matches_hungarian.csv`, keeping only participants present in all four source record types. It regenerates only `data/answers.csv` and `data/crt_rme_demo.csv`; `data/statement_properties.csv` and `data/statement_published.csv` are committed as-is and are not rebuilt by any script.
- **Score formula:** `commonsensicality = sqrt(consensus × awareness)`, where `consensus = 2 × |I_agree_mean − 0.5|` and `awareness = others_agree_mean` if the majority agrees, else `1 − others_agree_mean`. Implemented in `utils.py` (`individual_commonsensicality`, `statement_commonsensicality`), which returns a 0–1 value; the API passes that through and `app.js` multiplies by 100 for display. The exception is `get_country_matrix()` in `server.py`, which re-implements the formula inline and returns 0–100. `static/intro.js` also restates both the statement and the individual formula (`introStmtCalc`, `introIndivCalc`) so the panel intro cards' try-it controls can recompute in the browser, and `stmtCalcHtml()` in `app.js` restates the statement formula for the worked calculation in every statement modal. A formula change must update all four. On screen every square root is drawn with its bar over all the terms under it (Josh's request): `sqrtHtml(inner)` in `app.js` (an SVG radical sign stretched to the terms' height, continued by `.sqrt-arg`'s top border; `.sqrt*` in `style.css`; the two intro cards' static `.intro-formula` spans carry the same markup), and the LLM level-curve chart's pointer probe draws its own radical as an SVG path (`.llm-lvl-rad`). Never write "√(" in visible text. A container rule like `.x span { display: block }` breaks `.sqrt`; use a child selector (`.x > span`). (`get_statement_countries()` scores each country through `statement_commonsensicality()`, passing the country in its `statementId` column, so it needs no change.)
- **API base URL is computed dynamically** in `app.js` from the `<script src>` of its own tag, so it resolves correctly under both local dev (`/api`) and the production reverse-proxy path (`/report/api`, since nginx also proxies a separate, unrelated service at bare `/api`). Never hardcode `/api/...` in new frontend code — always use the `` `${API}/...` `` pattern.
- **The 10-ratings-per-statement threshold is duplicated and must stay in sync.** Its main home is the default `min_ratings_per_statement=10` in `utils.py` (alongside `min_statements_per_user=5`). Every caller uses these defaults, so they drive Individual Scores, Statement Scores, Design Points, Group Comparison, and the Design Point Coverage "Calculated" count. The "10" and "≥5 statements" strings in `index.html` and `app.js` copy and tooltips restate these values (including the statement modal's "How each country answered" summary and the Countries "Share who agree" notes), as do the panel intro cards (their copy in `index.html`, and `INTRO_MIN_REF_RATINGS` in `static/intro.js`). - **LLM numbers are recomputed, not copied.** `llm_evals.py` recomputes each model's consensus, awareness and commonsensicality exactly from its ratings (models.csv rounds to 4 decimals, which turned Claude 3 Sonnet's 61.5466% into 61.6%; the published text has the same slip) and its "Beats" from exact head-to-head counts on each participant's statements (sqrt is monotone, so it compares products of match counts; ties are never broken by float noise). The ensemble R² is recomputed too (`_oos_r2()`, `ENSEMBLE_*`: OLS with an intercept, sklearn's shuffled 50-fold split with seed 100, as the paper's notebook does it; on the paper's 35 models it reproduces their 0.361 exactly, and on all 44 it is 0.373; `get_summary()` sends it as `ensemble`). The published figures it can't recompute (the size regression) are `PAPER` in `llm_evals.py`, which also keeps the paper's split-half .60 (.58–.61) for the Overview and Home bars. The split-half benchmark itself is recomputed: `_load()` splits the participants into two random halves of 1,023 for seeds 0–999 (`SPLITS`), scores every statement in each half (`_crowd_scores()`, the same formula), and correlates the halves (mean .596, 95% of splits .580–.612, about 1 s at startup; `get_summary()` sends it as `split_half`), and `get_split(seed, statement)` returns one split's r, every statement's score in each half (`scores`, for the population story's scatter plot) and one statement's raters in each half (`split_half.rs` holds all 1,000 splits' r, for its histogram); the panel's average model score is the computed mean of all 44 (71.9%, SD 9.8). The population story's worked example defaults to the paper's own statement (`EXAMPLE_POPULATION`); the individual story's opens on `LLM_IND_EXAMPLE` in `llm.js`, with the paper's (`EXAMPLE_INDIVIDUAL`) one click away. Optional inputs: `data/llm_evals/model_meta.csv` is hand-curated (developer, `open`/`proprietary`, release month, `in_paper` (unused), the paper's LMArena score of 16 Aug 2025 for 24 models, `params_b` and `size_family` for the 23 models in the paper's size regression, from its notebook, and `method`: `probabilities` or `sampling`, from the paper for its 35 and from the ratings' granularity for the rest). `leaderboard.csv`/`human_reference.csv` (bootstrap intervals, shown in tooltips) and `features.csv` (feature gaps with 95% intervals; point estimates match the paper's bootstrap means to a few hundredths) are written by `build_llm_leaderboard.py` (numpy/pandas, offline, seeded, so reruns are byte-identical). `extract_llm_evals.py <llm-evals.html>` regenerates the other CSVs and the SVG from the study's standalone page (`commonsense-platform/client/public/llm-evals.html`, built by `open-llm-commonsense-eval/website/generate.py`); rerun it when that page is updated. The page stores the platform's raw property flags; the script converts them to this app's `fact`/`physical`/… vocabulary (that page's own filter labels for figure-of-speech and reasoning are inverted). **Rerun `build_llm_leaderboard.py --ratings-dir <open-llm-commonsense-eval>/data/model_ratings --fix-rounding` after every `extract_llm_evals.py` run**: the website rounds P(yes) to 4 decimals, which turns values just under 0.5 into a yes (Mistral-7B's per-statement ✓ marks were 2 points off its published consensus), and `--fix-rounding` rewrites those cells as 0.4999.

## Other `.scripts/` subdirectories

- `besample/` — recruitment sampling strategy and analysis for the Besample platform. `.scripts/besample/statement_sampling_strategy.md` documents the algorithm for choosing which 15 statements to assign new participants from under-sampled countries, to maximize coverage of the statement × country matrix.
- `statement-generation/` — LLM-based generation of candidate statements (via OpenRouter, using `generate.py --model-name M`/`generate.ipynb`) tagged against the same six binary properties as `statementproperties/`. `judge.py --gen <gen-model> --judge <judge-model>` (both required) has a second model re-classify them, writing to `data/<gen-model>/evaluations/<judge-model>/statements.csv` (`/` in model names becomes `--`). `judge_batch.py` is a helper module, not an entry point. Batch mode is chosen by adding a `:batch` suffix to the judge model name; it prompts `[y/N]` before submitting, and closed or declined stdin leaves the batch unsubmitted. Rerun the same command to collect results. `judge_published.py` applies the same judge to the platform's published statements through subcommands: `prepare` (free snapshot), `judge --model-name M` (paid), and `status` (free). `judge_published_typesafe.py` classifies the same snapshot with TypeSafe's `typesafe/jev-1.13` (through OpenRouter; needs `typesafe-sdk`) and writes probabilities to `existing/published/typesafe/<model>/`, which the explorer's TypeSafe Judgments page reads (the audit page and `status` don't). These scripts make **paid API calls**: preview with `--random-prompt-view`, or use `--limit 1 --workers 1`. The Design Point Coverage page treats every `data/<model>/statements.csv` as a generator's output. That's why published-statement results live in `existing/published/`, and why nothing else should be written under `data/`. The folder also has its own standalone stdlib explorer, `python .scripts/statement-generation/server.py [--port N]`, run from repo root; it also defaults to 8080, so it conflicts with the visualize server. See its `README.md`. Requires `OPENROUTER_API_KEY` in the environment or `.scripts/statement-generation/.env` (not committed); its own `requirements.txt` is separate from the CI one. The scripts resolve paths from `__file__`, so they work from any directory (the README runs them from repo root). The exception is `check_remaining.py`, a free check of the key's remaining OpenRouter credit, which reads `.env` from the working directory and prompts for the key if it isn't found.
- Root-level notebooks/scripts (`analysis.ipynb`, `dashboard.ipynb`, `geo.ipynb`, `recover_demo*.py/.ipynb`, `platform_sampling.ipynb`, etc.) are exploratory analyses over the data above; they are not part of any automated pipeline and may depend on intermediate CSVs (e.g. `matched_results_after_cem*.csv`, `triplet_results_*.csv`) generated by earlier, undocumented runs.

## Working in this repo

- There is no test suite or linter to run. Validate changes to `.scripts/pull_data.py` or `.scripts/visualize/` by running them directly (see above).
- Large CSVs at the repo root and in `individuals_timed.csv` are committed data, not generated artifacts — don't regenerate or reformat them incidentally.
- **Pushing to `main` triggers the full pipeline** (data pull, commit, image rebuild, ECS redeploy). Keep code commits separate from data updates; automated commits use `Updated data at <date>` and append to `updated_at.txt`. `AGENTS.md` holds parallel guidance for other agents (style, commit conventions); keep the two consistent.
- `.scripts/visualize/data/` **is** committed, but CI never commits it: the "Commit data changes" step runs *before* `update-data.py`, so CI's rebuilt files only go into the Docker image. The committed copy is whatever a developer last rebuilt and committed by hand, so it lags the deployed site, and running `update-data.py` locally usually leaves it modified in `git status`. Commit those changes deliberately, never bundled with unrelated code.
